Aurora Admin Onboarding Guide

How Aurora fits together

Four pieces work together. Knowing which one owns a job tells you where to look when something breaks.

PieceWhere it runsWhat it owns
Aurora serverYour Windows PCAccounts, passwords, movies, shows, who is an administrator
Aurora GuardYour Windows PC, port 8922Limits, expiry, plans, resellers and credits, announcements, the Admin PIN, the audit log, playback quality
Aurora appsCustomers' phones, TVs, browsers: web, Android and Fire TV, iPhone, Apple TVEverything customers see. They talk to the Aurora server and the Guard
WebsiteNetlifyDownload page, the /admin/, /channels/ and /reseller/ pages, /survey/results/ and /status/

The path of a request

  1. A customer signs in. The app asks the Aurora server, which checks the password and returns a token.
  2. The app sends that token to the Guard with each request. The Guard asks the Aurora server who the token belongs to, so it never keeps its own passwords.
  3. The Guard decides what that person may do: customer, reseller, moderator or administrator.
  4. Before playback, the Guard checks expiry, hold and the connection limit. The Guard ends a session that breaks a rule.
  5. Live TV and movies stream from your provider or the Aurora server straight to the app. The app sends back a short health report after each viewing.

What this means for you

  • Aurora server down: nobody can sign in, and nothing plays.
  • Guard down: customers may still play, but limits, expiry and every admin tool stop. Fix it first.
  • Website down: only downloads and the web admin pages are affected. The apps keep working.
  • Roles are decided by the Aurora server plus the Guard. Make someone an administrator in the Aurora app and the server is updated for you.

Roles and access

Aurora has five kinds of account, and each one reaches a different set of tools. The rule that matters most: the Aurora Guard, not the app, decides what a signed-in account may do, so hiding a button never counts as security.

How each side decides

  • Aurora decides who is an administrator. The app shows the Admin menu to any account Aurora marks as one. The two owner usernames, johnny4091 and countryboy89, also always see it.
  • The Guard checks every admin request itself. It asks Aurora whether the caller's own token belongs to an administrator, so a different user id cannot fake it.
  • Moderators are checked against an allowlist of routes in the Guard. A moderator's call to Users, Resellers, credits, Server health, updates, plans or the provider login is refused with 403.
  • Resellers are limited by ownership. Every reseller call is checked against the customers that reseller created.

Rules that stop mistakes

  • A reseller cannot also be a moderator or an administrator.
  • Making an account an administrator clears its moderator flag.
  • You cannot remove your own administrator access, and the last administrator cannot be removed.
  • Administrator accounts are never limited or switched off by the Guard.

Before you touch anything

Admin changes reach real customers within a minute, so read these rules first. Most expensive mistakes here come from changing something for everyone when you meant one person.

The ground rules

  1. Use your own named account. The audit log records who changed what by the name you signed in with. Never share a login.
  2. Look before you change. Open a customer's page and read it before you save. Limits and end dates apply at once.
  3. Prefer the per-person switch over the "everyone" switch. Buttons that say "for everyone" (provider movies and TV, maintenance mode, Playback, Required updates) affect every account.
  4. Do not delete accounts you did not create. Deleting removes the server account and its history. Credits are not refunded.
  5. Never paste a secret into chat, a message or an announcement. That includes the Aurora API key, the provider login, the certificate password and the Admin PIN.
  6. Check the audit log after a busy session (Admin → Audit log). It is the record you will need if something looks wrong later.

The Admin PIN

The Admin PIN is a 4-digit code that sits in front of Admin → Resellers, Admin → Users and the credit requests. Its job is to stop another administrator you add from opening money and customer data.

  • Set it first. Open Admin → Resellers and type a PIN under "Admin PIN". Do this before you add anyone else as an admin. Whoever sets it first becomes the one who can change it.
  • It is tied to each sign-in. Every administrator, including you, types it once per sign-in. It asks again after 30 quiet minutes, and changing the PIN locks every session again.
  • Wrong tries lock it. Five wrong tries on one sign-in, ten from one internet address, or thirty in all, lock it for 15 minutes. The wait is counted per sign-in and per address, so signing in again does not reset it.
  • Changing or removing it needs the current PIN. Adding or removing an administrator also needs it.
  • If you forget it: put "resetResellerPin": true in the Guard's config.json, restart the Guard, then set it back to false and make a new PIN.

What the PIN does not protect

Any administrator can still open the Aurora server's own dashboard and see the user list there. The PIN protects what Aurora keeps: device limits, plans, contact details, reminders, resellers and credits. Give Aurora administrator access only to people you trust with that.

Signing in and where the tools live

You sign in to Aurora with your own Aurora username and password, exactly like a customer. The difference is what the profile menu shows afterwards.

In the app

  1. Sign in on the Android phone, Fire TV, iPhone or iPad app (or the web app, if you have its address).
  2. Open the profile menu (your initial, top right) and choose Admin. Moderators see the same entry with a shorter menu.
  3. Use the menu beside the page title to switch tabs. Refresh reloads the current tab.
  4. The Apple TV app has no Admin screens. Use a phone, a tablet, a Fire TV or a browser.

If the Admin entry is missing, work down this list:

  • Is the account an administrator in Aurora (server dashboard → Users → the account → allow management)? Without that, the Admin menu does not appear.
  • Are you on a recent app version? Install the newest APK or TestFlight build, then sign out and in.
  • Is the profile in Kids mode? Admin is hidden there.

Your first week

Work through this in order. Every step is safe to do on a live system if you only read, or if you use a test account you made yourself.

Day 1: get in and look around

  • [ ] Sign in and open Admin from the profile menu.
  • [ ] Read Overview. Note which health-check lines are green.
  • [ ] Open /health on your Guard address from a phone off Wi-Fi and confirm it answers.
  • [ ] Ask the owner to set the Admin PIN (Admin → Resellers), then type it once to see how it behaves.
  • [ ] Read the last 20 lines of Audit log to see what normal changes look like.

Day 2: customers and money

  • [ ] Open Users, filter by Ending soon, and open one customer without saving anything.
  • [ ] Read every plan in Plans: price, length, connections, categories.
  • [ ] Open Resellers, read the list and one reseller's credit ledger.

Day 3: talking to customers

  • [ ] Open Inbox and Support. Reply to one conversation, then mark it solved.
  • [ ] Send a one-hour Info notice from Announcements that says "test", then remove it.
  • [ ] Read Feedback and Playback problems to learn what viewers complain about.

Day 4: the live service

  • [ ] Read Live TV: the source, the stream type and the categories. Change nothing.
  • [ ] Read Server health: processor, memory, disk, streams.
  • [ ] Open Channels and Channel reports to see what a fix and a report look like.

Day 5: practise on a test account

  • [ ] Create a free-trial customer called something obvious like test_yourname.
  • [ ] Put a plan on it, change its device limit, then put it on hold and release it.
  • [ ] Delete the test account when you finish.

Customers: users, limits, plans and renewals

A customer is a server account plus a record in the Aurora Guard that holds a device limit, an end date, a plan and a few switches. Everything on the Users tab edits that record, and the Guard applies it within a minute.

The Users page

  • Time requests at the top lists customers asking for more time. Approve or deny from here or from Inbox.
  • Provider movies and TV has one button to turn that feature on or off for everyone. Use a customer's own page to change one person.
  • Admins and moderators lists who has staff access and lets you add or remove either one at any time.
  • Users is the list. Search by name, and filter by All, Active, Disabled or Expired. Each row shows devices in use against the limit, with a red Over limit tag when someone is above it.
  • Select turns the list into bulk edit: tick people, then change the limit, add days, set a date, clear the end date, apply a plan, or disable or enable them together.
  • Add user creates an account. Give it a plan at the same time so the limit and end date are set in one step.

What the Guard enforces, every minute

  1. Expired accounts are disabled in Aurora (IsDisabled). Accounts it disabled are enabled again once the date is extended.
  2. Devices over the limit are signed out. The newest devices go first. Each one gets a message, playback stops, and the device is removed so it must sign in again.
  3. Administrators are never limited or disabled.
  4. Nothing is enforced in dry run. While "dryRun": true the Guard only writes [dry run] would ... lines to its log. Check Admin → Users → Enforcement for the last check.

Plans

Plans are what you sell. Each has a name, a price, a length in months or days, a number of connections, and either all Live TV categories or only the ones you tick. A plan can also include the provider's movies and shows.

  • A plan is copied onto a customer. Changing or deleting a plan later does not change what someone already has.
  • Aurora records the price you set; it does not take payments.
  • Admin → Plans shows what came in this month and last month, and every subscription in a history list.
  • Discount codes are made on the website's /admin/ page. A waiting discount shows next to the customer, and the first paid plan it works on is recorded at the discounted price.

Renewals and extension requests

  1. A customer sees plan-ending notices in the bell at their reminder days. Settings → My account has a Request an extension button (one waiting at a time, four a month).
  2. The request appears in Users, Inbox and as an alert if you set a webhook. Pick how long to add (7 days to a year) and approve or deny with an optional message.
  3. Approving adds time to whichever is later, today or the current end date, so paid time is never lost. It also switches the account back on if the Guard had switched it off.
  4. Customers a reseller created send their request to that reseller first. You still see it, tagged with the reseller's name, but it only needs you when that reseller is suspended.
  5. An account that has already expired is switched off and cannot sign in to ask. It has to contact the person who sold it.

Sign-ups and referrals

  • Website sign-up is off until "signupEnabled": true is in the Guard's config.json. A sign-up creates the server account, starts a free trial (two days by default) and records the email. One account per email.
  • A referral code gives both people free days (referralDays, default 7; 0 turns it off). A code works in the first 14 days of an account, once. A free-trial account can neither use nor give a code.

Resellers and credits

A reseller is a server account (not an administrator) that you give credits to. They spend credits to create and renew their own customers, and they can only ever touch customers they created. This tab is behind the Admin PIN.

How credits work

  • One credit is one connection for one month. A plan costs its Reseller credits value (set in Admin → Plans). If that is blank, the cost is connections × months.
  • Free trials cost nothing. A trial lasts two days. Each reseller gets up to resellerTrialsPerDay (default 5) a day.
  • The balance can never go below zero. Each reseller has one change in progress at a time, so a double-click cannot spend credits twice. The server password is set before credits are taken.
  • A customer a reseller deletes is not refunded.

What a reseller can do

They sign in with their own account and open Reseller panel in the profile menu, or use the reseller website at /reseller/. Both have the same tools.

  • Create customers (username, password, name, email, phone, note), choosing a plan or a free trial. A new customer starts with the same Aurora settings the first administrator has.
  • Renew with any plan they may sell, one customer at a time or in bulk from Needs renewing. A bulk renewal is checked against their credits first and is all or nothing.
  • Reset a password (shown once with a welcome message to send), sign out all devices or just one, put a customer on hold or release them, delete their own customer.
  • Switch provider movies and TV, adult channels and reminder days for a customer, and copy a ready-made reminder message.
  • Search, filter (Active, Ending soon, Expired, Trial, On hold), sort and export the list to CSV.
  • See Watching now (what their customers are playing, refreshed every 20 seconds) and a customer's Playback quality.
  • Send a notice shown only to their customers (up to five at once, one hour to 14 days).
  • Set contact details (name, phone, WhatsApp, email, a note) that their customers see under Help & support.
  • Ask you for credits, and set alerts to Telegram, Discord, ntfy or a web address for extension requests, low credits and an ending-soon list.
  • Add sub-resellers and send them credits. A sub-reseller sees only its own customers and cannot add sub-resellers.

A reseller cannot open any other admin page, see other resellers, or see another reseller's customers. If a customer asks for an extension, it goes to their reseller first.

Habits that keep resellers healthy

  1. Give a small starting balance, then top up on request. It is easier than clawing credits back.
  2. Check the ledger when a balance looks wrong. Every change has a reason and a name.
  3. Ask a reseller who keeps hitting low credits whether they want a larger top-up or a different plan mix.
  4. Never share one reseller login between people. Add a sub-reseller instead.

Live TV and channels

Live TV comes from your provider, so most live problems are provider problems. Aurora adds channel lists, your own custom channels, backup streams and a viewing-quality report.

Where channels come from

  • Provider channels are listed by the Guard from your provider and cached. Categories, favourites and the guide (EPG) are built from them.
  • Custom channels are ones you add yourself: a name, a stream address, a logo and a category. Manage them in Admin → Channels or on the website at /channels/.
  • Backups: a channel can have one or more backup stream addresses. If the main one fails, the player switches on its own.

How the backup switch works

The player watches the first picture. It moves to the next backup when any of these is true:

  1. The stream reports an error or the source fails.
  2. Nothing has stalled the picture for about 8 seconds while it is trying to play.
  3. No first picture has appeared within the no-picture limit after tuning.

It tries each backup once, then stays on the last one. The Android and Fire TV apps do this natively. On iPhone the same rules apply in the live player. If a customer says a channel "does nothing", look at the on-screen reason shown on the player and test the backup address yourself in a player like VLC.

Testing a channel

  1. Open the stream address in VLC or the server's web player on your own PC.
  2. If it plays there but not in Aurora, check the format (HLS .m3u8 is the safest) and that the address does not need a login.
  3. If it fails everywhere, it is the provider or the source. Add a backup and tell the provider.

Reading viewing quality

Every viewing reports its health: minutes watched, stalls, start time (average and slowest), slow starts and failures. Open it from a customer's page (Users → customer → Playback quality) or from the reseller panel. Hints are written for you:

  • Many stalls with a small buffer → turn on Large buffer in the player.
  • Low stream speed → the customer's internet, or the provider's server, is the limit.
  • Many failed starts for everyone → provider trouble, not the customer.

Rules of thumb

  • One customer with problems is usually their network. Many customers at the same time is the provider or your server.
  • Do not delete a channel because of one failure. Add a backup first.

  1. Open Overview. Is the Guard up, is the server reachable, is anything flagged?
  2. Open Inbox and clear what is waiting.
  3. Glance at Devices to see the normal evening load.
  4. Look at the daily summary if you have alerts turned on (Telegram, Discord or ntfy).

What "normal" looks like

  • A steady number of sessions that rises in the evening.
  • No customer with several devices at once beyond their limit.
  • Few failed logins. A spike of failed logins from one address is a guess-the-password attempt: the Guard already slows it down, and you can see it in the Audit tab.

The Audit log

Every administrator action is written down with the time and who did it: credits changed, a password reset, a PIN set, an admin made or removed. It is read-only. Use it to answer "who did that?" and to see that your team follows the rules.

Before you escalate

  1. Reproduce it: which customer, which app, which device, what time.
  2. Check Devices and Playback quality.

Announcements, support and maintenance

Announcements

Admin → Announcements shows a message inside every customer's app. Choose who sees it (everyone, one customer, or one reseller's customers), how long it stays (one hour to 14 days) and whether it is a normal notice or a maintenance notice. Resellers can send notices to their own customers only, up to five at once.

  • Keep them short: what, when, what to do.
  • Remove a notice when it stops being true.

Support details

Customers see contact details under Help & support. Yours are the default. A reseller can set their own, and their customers see those instead.

Maintenance

  1. Post a maintenance announcement at least a day before.
  2. Do the work when few people are watching (check Devices first).
  3. Restart in this order: the Aurora server first, then the Guard.
  4. Open the /status/ page, then sign in from the app to confirm.
  5. Remove the announcement.

Updates and releases

Every change goes through GitHub. When it is merged, GitHub builds the Android and Fire TV app and publishes a release containing Aurora.apk, aurora-guard.js and aurora-guard.json. The iPhone app is built and sent to TestFlight automatically on every push.

If an update goes wrong

The Guard keeps its settings in aurora-guard.json and its data folder, so reinstalling the script does not lose customers. Put the previous aurora-guard.js back and restart it, and tell the developer what happened.

Running the Guard

The Guard (aurora-guard.js) is a single Node file on your Windows PC. It listens on port 8922, talks to Aurora, and enforces limits, expiry, plans, credits and the Admin PIN. It has no extra packages to install.

Forgotten Admin PIN

  1. Stop the Guard.
  2. Open aurora-guard.json and add "resetResellerPin": true.
  3. Start the Guard. The PIN is cleared and the audit log records it.
  4. Remove that line, restart, and set a new PIN in Admin → Resellers.

Starting, stopping, checking

  • Run it so it starts with Windows (a scheduled task or a service wrapper) so a reboot does not take Aurora down.
  • Check the /status/ page after any restart.
  • If the port is in use, another copy is running. Stop it first.

Network

The Guard must be reachable from the internet on port 8922 the way the Aurora server is on its own port. If customers can reach the server but not the Guard, check the router's port forward and the Windows firewall for 8922.

Security and privacy rules

  1. Treat customer data as private. Names, emails, phones and viewing history stay inside the team. Never paste them into public chats, tickets or AI tools.
  2. One person, one login. Never share an admin or reseller login. Add the person as an administrator or moderator instead.
  3. Give the least access. Prefer a moderator or a reseller over an administrator. Remove access the day someone leaves.
  4. Keep the Admin PIN to people you trust. It protects Resellers, credit requests and Users from an administrator you added recently.
  5. Send passwords privately and once. The app shows a new password a single time. Do not store it in notes.
  6. Do not edit server users by hand unless you must. Use Aurora so limits, plans and the audit log stay in step.
  7. Keep the server dashboard private. An administrator can still use the Aurora server's own dashboard, which the Admin PIN does not cover.
  8. Update promptly. New releases carry fixes. Check Admin → Server weekly.
  9. Read the Audit log now and then. Odd actions at odd hours mean a shared or stolen login: reset it.
  10. Never publish keys. Provider addresses, tokens and the Guard config do not belong in screenshots or messages.
